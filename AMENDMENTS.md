# Amendments

Protocol (implementation plan `aart_implementation_plan_v1.md` §7): any change to an S0-frozen interface's **public shape** (a field added/removed/retyped on a `@aart/types` schema, a method signature changed on `AartStore`, `@aart/expr`'s resolver function signature changed) after the `interfaces-frozen-v0` tag requires an entry here — date, discovering session, what changed, why, which other sessions/packages are affected — plus a loud (not silent) backward-compatibility flag if applicable. Internal refactors that don't change a public interface's observable shape don't need an entry.

This file also carries S0's own record of every place the two source documents (`aart_architecture_v1.md`, `aart_product_spec_v2.md`) left a shape underspecified and S0 had to make a concrete, load-bearing choice to freeze something buildable — per this session's own brief: *"If you hit an apparent contradiction on contact, do NOT silently resolve it: pick the amendment-log-supported reading, note it in your report, and record it in AMENDMENTS.md."* None of the entries below are contradictions between the two documents (the multi-round consistency program the docs went through left none on contact) — they are gaps: a method signature never given in TS anywhere, a field name never spelled out, a type never given a literal TS block. Each is flagged here rather than left implicit, so Wave-1 sessions know it was a deliberate S0 choice, not an oversight, and can propose a change through this same protocol if it doesn't fit their needs.

## 2026-07-10 — S0 Foundation

### A1 — `AartStore` per-member method signatures designed from scratch
Neither document gives explicit method signatures for any of the 16 `AartStore` sub-interfaces (`WorkflowStore`, `RunStore`, `WaitStore`, ... `StandingApprovalStore`) — spec §28.3 gives one-line prose contracts, architecture §5.3 gives SQL columns. `packages/store/src/types.ts` designs a consistent `get`/`put`/`list` shape per member, plus the specific query methods actually implied by how each store is used elsewhere in both documents (e.g. `WaitStore.listDue(now)` for the scheduler-ticker seam, `SignalStore.findUnconsumedMatch` for the early-arrival check). Affects: every Wave-1 package that reads/writes through `AartStore` (S1, S2, S4, S6, S7). Not a contradiction — a genuine design gap S0 had to fill to ship a buildable interface.

### A2 — `RunStore.hasDedupeKey` / `RunStore.recordDedupeKey` added
Architecture §4.4.2's exactly-once resume dedupe ledger has no store-interface member anywhere in either document — without it, S1's dedupe-check-and-transition pattern would have nothing to call inside `transact()`. Added two methods to `RunStore`; the fs adapter co-locates the dedupe-consumed set inside the same `runs/<runId>.json` file as the `RunRecord` (architecture §5.8's documented mechanism), so staging both through the same `transact()` buffer coalesces them into one atomic write. Affects: S1 (engine, the actual caller).

### A3 — `job_queue`'s fs directory location
Architecture §5.2's fs layout listing does not include a `job_queue` directory, even though `job_queue`'s shape (including `lease_expires_at`/`reclaim_count`) is explicitly S0 scope "from the start" (architecture §4.7/§5.3). Added `.aart/job-queue/<runId>.json`, following the same directory-per-collection convention as every other listed member. Affects: S1 (claim path), S2 (worker liveness — lease renewal, reclaim sweep, graceful shutdown are still S2's to build; S0 only froze the shape and basic get/put/list-claimable primitives, not the race-safety/reclaim logic itself).

### A4 — `EnvironmentStore` dual-keyed by both `id` and `name`
Architecture §5.3's SQL table primary-keys `environments` on `id`; architecture §5's one-line contract states "keyed by name." `DeploymentStore` references environments by `environmentId` (an id, matching the FK), while human-facing lookup (dashboard/CLI) naturally wants lookup by name. Rather than picking one and contradicting the other passage, `EnvironmentStore` exposes both `get(id)` and `getByName(name)`.

### A5 — `StandingApproval.id` added beyond spec §17.6's literal shape
Spec §17.6's `StandingApproval` TS block has no `id` field (it types the policy shape only: `maxRiskTier`/`capabilities`/`grantedBy`/`expiresAt`). Architecture §5's `AartStore` extension states `standingApprovals` is "keyed by id," and architecture §5.3's SQL table backs this with `standing_approvals (id PK, ...)`. Added `id: string` to `@aart/types`' `StandingApprovalSchema` so the type the store actually persists can be keyed as architecture requires. Affects: S4 (writes standing approvals at policy-authoring time).

### A6 — `Workflow.needsReview` / `Workflow.promotionBlocked` added to the canonical type
Spec §23.4 names "block promotion" and "mark workflow version as needs review" as correction outcomes; architecture §5.3 backs them with SQL columns (`workflows.needs_review`, `workflows.promotion_blocked`) but neither document adds them to spec §14.1's literal `Workflow` TS block. Added both as optional booleans directly on `WorkflowSchema` (`packages/types/src/workflow.ts`), following the same flag-and-add pattern architecture already uses for `RunRecord.flag` and `Trigger.dedupeKey`, rather than inventing a parallel store-only query surface for two booleans governance's promotion path (architecture §7.1/§9.4) needs to read at gate-check time. Affects: S4 (`computePromotionState`'s refusal-to-promote check, per architecture's A30 fix), S2 (environment/deployment integration), S6 (writes these fields as correction outcomes).

### A7 — `StepTrace.postHocCorrected` added to the canonical type
Same pattern as A6: architecture §5.3's `step_traces.post_hoc_corrected` column (F5 fix) backs spec §23.4's "update current run output" correction outcome, with no home on spec §19.2's literal `StepTrace` TS block. Added as an optional boolean on `StepTraceSchema`. Affects: S6 (writes it as a correction outcome).

### A8 — Engine-code schema-version tag field named `schemaVersion`
Architecture §4.7 requires "every persisted `WaitCondition`/`RunRecord`" to carry a schema-version tag "distinct from `schema-version.json`'s whole-store migration watermark" but never gives the field an exact name. Named it `schemaVersion` (required, non-optional, on every `WaitCondition` union member and on `RunRecord`) — deliberately distinct from the migration watermark's own `version` key (`schema-version.json: { version: N }`) to avoid the two being confused in code or logs. Affects: S1 (tests resume-time version-compatibility behavior against this exact field, per this session's own DoD note).

### A9 — `store-records.ts` types (`Deployment`, `Environment`, `Schedule`, `PromptRegistryEntry`, `SchemaRegistryEntry`, `PackManifest`, `Correction`, `RejectedTrigger`) derived from architecture §5.3's SQL columns
None of these eight types has a literal spec TS block — spec describes them in prose/YAML examples (§27 deployment modes, §29 scheduling, §16 packs) or, for `Correction`, a JSON example (§23.3). Their Zod shapes in `packages/types/src/store-records.ts` are derived from architecture §5.3's SQL table columns (the one place a complete field list exists for each), camelCased to match this module's convention elsewhere. A few fields were deliberately left open (`z.string()`) rather than closed enums where neither document gives a complete enumerated set — `PackManifest.approvalStatus` (only "unapproved"/"approved" are named in prose, ADR-12/§16.2, with no closed list), `Scorer.kind` (spec §24.3 lists 12 built-in kinds in prose but the type itself is `kind: string`, and a pack/custom scorer shouldn't be rejected by `@aart/types`), `RetryPolicy.backoff`/`retryOn` (architecture §4.2 writes `backoff: "exponential" | ...`, explicitly leaving the rest open) — none of these fabricate enum members the source documents don't actually list.

### A10 — `CapabilityCheck`, `RedactFn`, `BlockImplementation.execute` modeled as plain TypeScript function types, not Zod schemas
This package's DoD asks for "every type in architecture §2.1's inventory... as a Zod schema with a derived `z.infer` type export." These three are function-type dependency-injection seams (a callback signature engine calls, never JSON data anyone validates at a runtime boundary) — modeled as plain `type X = (...) => Y` instead. See `packages/types/src/governance.ts` and `block.ts` for the in-code rationale. Every other type in the §2.1 inventory (~30+ types) is a full Zod schema as instructed.

### A11 — JSON Schema derivation uses Zod 4's native `z.toJSONSchema()`, not the `zod-to-json-schema` package
Architecture ADR-01 names `zod-to-json-schema` as the (parenthetically "or equivalent") derivation mechanism. Verified during this session that the installed `zod@4.4.3` ships a first-party `z.toJSONSchema()` that correctly emits a `oneOf`-with-`const`-per-member shape for a `z.discriminatedUnion` (tested directly against both `WaitCondition` and `Trigger`). Used the native method instead of adding the third-party package as a dependency — same derivation guarantee, one fewer dependency, no risk of the third-party package's internal-representation assumptions drifting from Zod 4's actual internals. `packages/types/src/json-schema.ts`.

### A12 — TypeScript pinned to 5.9.3, not the newly-released 7.0.2
`npm view typescript version` resolved to `7.0.2` (TypeScript 7, the from-scratch native/Go reimplementation of the compiler) at the time this session ran. Deliberately pinned to `5.9.3` (the latest release on the mature 5.x line) instead — for a foundation layer eight parallel Wave-1 sessions build against immediately, the 5.x line's battle-tested ecosystem/tooling compatibility (declaration emit, project-reference/composite-build behavior, third-party `.d.ts` compatibility) outweighs being on the newest major. This is a devDependency choice, not a public-interface shape change, so it's recorded here for visibility rather than as a blocking amendment — bumping to 6.x/7.x later is a routine version bump.

### A13 — `packages/cli`'s `package.json` `name` field is `@team-monet/aart` directly
ADR-18 (A22/A28 fixes) states `@aart/cli` "is renamed/published as `@team-monet/aart`" with no separate rename mechanism described anywhere (no `publishConfig.name` override named in either document). Read this literally: `packages/cli/package.json`'s `name` field is `"@team-monet/aart"` from the start, not `"@aart/cli"` — the directory is `packages/cli`, the package name is not `@aart/*` at all, matching how every `npx @team-monet/aart ...` example throughout both documents already invokes it. It is the one package not marked `private` (ADR-18/A28).

### A14 — `examples/` subdirectories not pre-created
Implementation plan §2 says S0 "just creates the directory + a README stub." Read as: create `examples/` itself plus `examples/README.md`, but not `examples/redacted-legacy-b/` or `examples/redacted-legacy-a/` — S1 authors the guarded-loop fragment into the former (creating it as part of that work), S9 authors the latter "from scratch" (P19 amendment). Noted here since the plan's wording is compatible with either reading.

### A15 — pnpm build-script approval recorded in `pnpm-workspace.yaml`
`isolated-vm` is a native addon; pnpm 10's default security posture ignores its install script (`node-gyp rebuild`) unless explicitly approved. Ran `pnpm approve-builds --all`, which pnpm persisted as `allowBuilds: { isolated-vm: true }` in `pnpm-workspace.yaml` (committed) — without this, every fresh `pnpm install` (Wave-1 sessions, CI) would silently skip building `isolated-vm`'s native binding and the isolated-vm smoke test (and, later, S1's sandbox) would fail with a missing-binary error, not an obviously-native-addon-related one. Not an interface change; recorded here because it's exactly the kind of platform friction this session's smoke tests exist to surface, and the fix needed to be committed, not just applied locally once.

Also relevant to S5 (`@aart/mcp`'s YAML `uses`/`with` compiler, §14.2/§10.3) and S4 (governance's approval-summary/trust-surface-completeness test, ADR-17 — a new execution-affecting `Workflow` field should render in the approval summary the same as any other) if/when either session's own work touches workflow-level fields; flagged here so both can pick it up without re-discovering the gap themselves.

### A17 — SQLite adapter built on Node's built-in `node:sqlite`, not `better-sqlite3`/`sqlite3`
Neither document names a specific SQLite binding for architecture §5.1's "SQLite | Single-node production" adapter. S2 (`packages/store/src/adapters/sqlite/**`, the declared carve-out per implementation plan §3's preamble) uses Node's built-in `node:sqlite` (`DatabaseSync`) rather than adding `better-sqlite3` (or `sqlite3`) as a new dependency. Rationale: (1) the workspace already carries one native-addon platform-friction risk (`isolated-vm`, implementation plan Risk 3) — `better-sqlite3` is ALSO a native addon requiring a native build step, i.e. a second instance of exactly the risk class S0's smoke tests exist to surface, whereas `node:sqlite` ships inside Node itself (verified present and functional on the installed `node@22.22.2`, matching this workspace's `engines.node: ">=22"` floor — Node's sqlite support landed at 22.5); (2) zero new dependency footprint, consistent with this codebase's existing preference for built-ins over third-party packages where one suffices (A11's `z.toJSONSchema()` choice is the same pattern). `node:sqlite` currently logs a one-line `ExperimentalWarning: SQLite is an experimental feature` on first use — functionally inert (does not affect behavior or exit codes), left as-is rather than suppressed, so it stays visible to whoever operates this in production. `node:sqlite`'s `DatabaseSync`/`StatementSync` are synchronous, same programming model as `better-sqlite3` — every `AartStore` method built on top still returns a `Promise`, so this is invisible to callers either way. Not a blocking amendment (this is an implementation choice inside S2's own carve-out, not a change to any frozen interface's public shape) — recorded for visibility per A11/A15's established pattern, since a future session (S9, if it later needs to touch this adapter) or reviewer should know this was a deliberate choice, not an oversight.

### A18 — SQLite adapter stores `RunRecord.trace`/`waits`/`artifacts` as columns on `runs`, not architecture §5.3's literal separate `step_traces` table
Architecture §5.3's literal `runs` table has no column for `trace`/`waits`/`artifacts` — its design implies reconstructing `RunRecord.trace` via a join against a separate `step_traces` table. Two problems with implementing that literally: (1) `RunStore`'s frozen interface (`packages/store/src/types.ts`, S0-owned, outside this carve-out) exposes trace/waits/artifacts *only* as fields embedded in the `RunRecord` `get()`/`put()` round-trip — no `AartStore` member exposes step-trace-level SQL access independent of the parent `RunRecord`, so a separate table would have no reader; (2) reconstructing `RunRecord.waits[]` specifically from architecture's own `waits` table (this adapter's `WaitStore`) would be actively wrong — that table holds only the *current outstanding* wait per `(run_id, step_id)`, deleted on resolve (architecture §5.6/the `WaitStore.delete` contract), while `RunRecord.waits` is an ever-growing historical array (architecture §4.4 step 4: "RunRecord.waits array gets this WaitCondition appended") — a resolved-and-deleted wait can never be recovered by joining against the live `waits` table. Given S0's conformance suite requires exact round-trip fidelity (`toEqual` deep equality) and no interface consumer needs step-trace-level SQL querying today, `runs.trace_json`/`waits_json`/`artifacts_json` hold these arrays directly as the source of truth; architecture's literal `step_traces` table is left as documented future work (a real SQL-queryable table with no current caller and real dual-write drift risk is not built speculatively). `runs.schema_version` is also added beyond architecture §5.3's literal column list — a gap-fill, not a contradiction: `RunRecord.schemaVersion` (architecture §4.7/A8) was added to the frozen type after §5.3's column list was last written, so the SQL listing was never updated for a field the type already requires. Affects: S9 if it later builds a step-trace-level query surface — the physical layout to extend or supersede is documented in `packages/store/src/adapters/sqlite/schema.ts`'s module doc comment.

### A19 — `packages/store`'s `package.json` does not yet expose the SQLite adapter to sibling packages — ACTION NEEDED, outside this session's carve-out
S2's carve-out is `packages/store/src/adapters/sqlite/**` only — it does not extend to `packages/store/package.json` or `packages/store/src/index.ts` (both S0-owned). Those two files currently export only `"."` (the fs-adapter-backed main entry point); there is no subpath export for `adapters/sqlite/**`. Consequence, verified directly: no OTHER package in this workspace — including `@aart/server` itself — can currently `import { createSqliteStore } from "@aart/store"` or any subpath thereof; Node/TypeScript's `exports`-map resolution refuses any path not explicitly listed. **This session's own `@aart/server` code and tests deliberately do NOT depend on the SQLite adapter** (composition is via a caller-supplied `AartStore` — see SEAMS.md's `SharedRuntimeConfig.store` — and this package's own tests use `createFsStore`, already properly exported) precisely because of this gap, so it did not block S2's own DoD. It DOES block whoever eventually wires `aart server --store=sqlite:<path>` (most likely `@aart/cli`, S5, or S9's integration pass) from reaching the adapter at all. **Proposed fix** (one of, applied at the source per the amendment protocol's "gets it applied at the source" step — this session cannot apply it directly): add a `"./sqlite"` entry to `packages/store/package.json`'s `exports` map pointing at `dist/adapters/sqlite/index.d.ts`/`.js` (matching the existing `"."` entry's shape), OR re-export the sqlite adapter's public surface (`createSqliteStore`, `openSqliteStore`, `SqliteStoreHandle`, `CreateSqliteStoreOptions`) from `packages/store/src/index.ts` directly. Either is a small, low-risk, backward-compatible addition (adds a subpath, changes nothing existing). Affects: S5 (CLI's `aart server`/`aart worker` store-selection wiring), S9 (integration pass — this is exactly the kind of seam-that-didn't-converge Risk 5 names).

**S9 resolution (2026-07-10): RESOLVED.** Added `"./sqlite"` to `packages/store/package.json`'s `exports` map (pointing at `dist/adapters/sqlite/index.{d.ts,js}`, mirroring the existing `"."` entry) — see S9's own integration-fix commit. `@aart/store/sqlite` now resolves for any workspace consumer; `@aart/cli`'s `--store=sqlite:<path>` wiring uses it (Phase 2 item 9).

### A20 — Trigger-intake dedupe-key check is a linear scan, not an indexed lookup — scaling limitation, proposed fix outside this session's carve-out
Architecture §6.1's FLAGGED DIVERGENCE requires intake to check `Trigger.dedupeKey` "against previously-seen keys for that trigger/deployment before run creation." No `AartStore` member (the frozen 16 + job_queue/idempotency_ledger) persists a delivery-identity ledger independent of the `RunRecord`s a delivery produced — `packages/store/src/types.ts` is S0-owned, outside this session's carve-out, so this session could not add one itself. `packages/server/src/triggers/intake.ts`'s `findRunByDedupeKey` instead scans `store.runs.list({ workflowId })` (bounded to one workflow, not the whole store) and checks each run's own embedded `trigger.dedupeKey` for a match — correct, but O(n) in that workflow's run count rather than an indexed lookup, and it only catches a redelivery of a trigger that already produced a `RunRecord` (a delivery rejected for another reason first — e.g. `bad_hmac` — has no `RunRecord` to scan, so an immediately-following genuine redelivery with the same `dedupeKey` would not be caught by this check alone, though `rejected_triggers`' own audit trail still records both attempts individually). **Proposed fix**, for whoever has write access to `packages/store/src/types.ts` (S9, or a coordinator-approved amendment): add a small dedicated member, e.g. `RunStore.findByDedupeKey(workflowId, dedupeKey): Promise<RunRecord | undefined>` (adapter-implementable as an indexed lookup — SQL: `WHERE workflow_id = ? AND json_extract(trigger_json, '$.dedupeKey') = ?`, or a small secondary index) — S2's `findRunByDedupeKey` should switch to calling it once it exists, deleting the interim linear-scan implementation. Affects: S9 (real production throughput at scale), any session touching `@aart/store`'s frozen interface next.

**S9 resolution (2026-07-10): DEFERRED, accepted for v1.** `RunStore` is already a 16-member frozen interface with real adapters (fs, sqlite) built against it; adding `findByDedupeKey` now is a real interface-shape change this late in the build, for a bound (one workflow's run count) that is not a demonstrated production problem yet. Accepted as a documented v1 scaling limitation rather than an interface amendment — `intake.ts`'s `findRunByDedupeKey` now carries an inline comment pointing back to this entry. Revisit if/when a workflow's per-workflow run count is large enough for the linear scan to matter in practice.

### A21 — `computeApprovalState`: an empty `requiredGatesForMode` never vacuously auto-approves
Architecture §7.3's explicit mode->required-gates mapping states dev mode "requires nothing" (an empty array) in the same breath as "approval never auto-flips... dev is meant for throwaway iteration, not promotion." Read literally, "every gate in an empty set has passed" is vacuously true, which would auto-approve every dev-mode workflow immediately — directly contradicting "never auto-flips" one sentence later. `computeApprovalState(gates, requiredGatesForMode)` (`packages/governance/src/approval.ts`) resolves this by treating an empty `requiredGatesForMode` as never-satisfiable rather than vacuously satisfied. This is the only `requiredGatesForMode` value any of the four documented trust modes actually supplies (dev's — see `REQUIRED_GATES_BY_MODE`, `gates.ts`), so the rule is dev-mode-specific in practice without `computeApprovalState` needing a mode parameter to know it. Tested explicitly in `approval.test.ts` ("dev NEVER auto-flips to approved, even with every gate passed").

### A22 — Capability risk table gaps (`queue`, `db.read`) interpolated to Medium
Spec §31.0's capability taxonomy names 10 base capabilities; §31.1's risk table (the very next subsection) assigns an explicit risk tier to only 8 of them — `queue` and `db.read` are named in the taxonomy but never given a risk-table row (not a contradiction between the two documents, a silent gap within the SAME document). `riskForCapability` (`packages/governance/src/capability.ts`) interpolates both to Medium, by analogy by the table's own file.read (Low-medium) / file.write (Medium) pair, which establishes a one-tier "read is safer than write" delta within one resource family: db.read sits one tier below db.write's High -> Medium; queue is an external-system interaction comparable in kind to http/browser/llm (all Medium), not merely local like file.read. Any capability string outside the documented taxonomy entirely defaults to High (fail-closed, not fail-open) — see the same function. Affects: S1/S9 (capability closure risk is what the approval summary and `getGrantedCapabilities` both key off).

### A23 — `ApprovalTask`'s `runId`/`stepId` sentinel convention for workflow-VERSION-level decisions
`ApprovalTask`'s frozen shape (spec §13.5) is `runId`/`stepId`-keyed for a per-run wait-type approval (a `human.approval` step's decision). Architecture §7.2 requires PR-merge ingestion to write an `ApprovalTask` "going through the exact same... write path as a CLI/dashboard decision" — but a PR-merge (or a standing-approval auto-pass) decides a workflow VERSION's promotion eligibility (the `humanReview` gate) before that version has necessarily ever run; there is no real run/step to key off. Neither source document resolves this identity gap. `workflowVersionApprovalSubject(workflowId, workflowVersion)` (`packages/governance/src/approval-tasks.ts`) resolves it with a documented sentinel pair: `runId: "workflow-version:<workflowId>@<workflowVersion>"`, `stepId: "__gate:humanReview__"` — used consistently by every workflow-version-level `ApprovalTask` writer in this package (`recordPrMergeApproval`, `recordStandingApprovalDecision`). A genuine per-run `human.approval` wait's `ApprovalTask` always carries real `runId`/`stepId` from its own `RunRecord`/`WorkflowStep` and never goes through this helper. Affects: S2 (github trigger adapter calling `recordPrMergeApproval`), S8 (dashboard rendering approval tasks — should recognize this sentinel shape as "a version-level decision," not a malformed run reference).

**S9 flag (2026-07-10, pending reconciliation):** S5 independently filled the identical type gap for MCP/CLI-originated approval decisions with a DIFFERENT sentinel encoding (`SEAMS.md`'s S5 entry, "Load-bearing interpretive decisions": `runId: "version-review:<workflowId>@<workflowVersion>"`, `stepId: "humanReview"`). Two non-interoperable encodings of the same workflow-version-decision concept currently coexist. Tracked as this session's Phase 2 reconciliation item 2 — resolution recorded in a follow-up entry once decided (not yet resolved as of this merge commit).

## 2026-07-11 — S9 Integration — critical finding, not one of the pre-enumerated reconciliation ledger items

### A27 — `@aart/engine`'s `createTrackingSecretResolver` tracked the resolved secret's NAME, not its VALUE — redaction was silently a no-op end-to-end

**Severity: highest-priority correctness/security finding of the entire integration pass** — higher than the sentinel collision (A23), because this one meant the system's core security promise (ADR-10, "the single redaction chokepoint") was not actually functioning, in a way NO Wave-1 package's own test suite could have caught (each side's tests independently self-consistent, but wrong relative to each other's real contract) — discovered only by a genuine end-to-end test against the REAL merged `@aart/governance` `redactRecord`, exactly the class of bug a hardening wave's integration testing exists to catch that per-package testing against mocks structurally cannot.

**The bug:** `@aart/types`' frozen `RedactFn` contract, and `@aart/governance`'s real `redactRecord` (its only real implementation, `packages/governance/src/redact.ts`) — both explicitly documented, in-code, that the `resolvedSecretRefs: ReadonlySet<string>` parameter holds resolved secret **VALUES** ("the set's members are used directly as search values, which is only executable if they ARE the values, not just their symbolic names" — `redact.ts`'s own doc comment; architecture §7.9: "replaces any occurrence of that literal resolved value"). `@aart/engine`'s `createTrackingSecretResolver` (`packages/engine/src/redaction.ts`) — the ONE place in the engine that populates this set, threaded through every persist call site in the package (run-lifecycle.ts/step-executor.ts/wait-machine.ts, all via `applyRedaction`) — instead did `resolvedRefs.add(name)`, tracking the symbolic secret NAME (e.g. `"API_KEY"`) that was looked up, not the VALUE the resolver actually returned (e.g. a real API key). `redactRecord` would then scan persisted records for literal occurrences of `"API_KEY"` — a string that essentially never coincidentally appears in real execution output — instead of the real secret value, so **no real secret value was ever actually redacted from a persisted `RunRecord`/`StepTrace`/`ExecutionSnapshot` in the real merged system**, despite every one of `@aart/engine`'s own pre-integration tests passing.

**Why S1's own tests didn't catch it:** `@aart/engine`'s own `redaction.test.ts`/`step-executor.test.ts` tests were built self-consistently around the SAME (wrong) mental model — asserting `resolvedSecretRefs.has("API_KEY")` (the name) as correct/expected, and one test's own mock redactor derived its search value FROM the tracked name (`` `secret-value-for-${ref}` ``) specifically to round-trip against a same-shaped mock `resolveSecret`, which worked precisely because the mock happened to make name and value derivable from each other — never exercising `@aart/governance`'s actual value-based contract. `@aart/governance`'s own tests only ever fed `redactRecord` values directly (never through the engine's resolver-tracking mechanism), so they never observed the mismatch either. Each package was internally correct against its own understanding and its own tests; the two understandings simply didn't match — a seam-convergence failure by definition, and precisely why S9's DoD frames the whole hardening wave as verifying "every cross-session interface seam... end-to-end, not just per-package."

**How it was found:** `packages/mcp/src/real-context.test.ts`'s "redaction genuinely runs end-to-end" test — built during S9's composition-root wiring (reconciliation ledger items 3/4/5/11) — constructs a REAL `@aart/engine` `Engine` wired to the REAL `@aart/governance` `redactRecord` (not either package's own mocks) and asserts a resolved secret value never reaches the persisted store. It failed on first run; the persisted `RunRecord`'s trace showed the raw secret value `"super-secret-value"` completely unredacted, while the workflow DEFINITION's unrelated `{{ secrets.API_KEY }}` template text had been mangled instead (`"{{ secrets.[REDACTED:secret-1] }}"`) — the literal string `"API_KEY"` matching inside the template text itself, nowhere near an actual secret.

**Fix:** `packages/engine/src/redaction.ts`'s `createTrackingSecretResolver` now does `if (typeof value === "string") resolvedRefs.add(value)` — tracks the resolved VALUE (guarding against `undefined`, since `Set<string>` can't hold it and `redactRecord` has no defined behavior for a non-string search value). No other file in the engine needed to change — every consumer already threads the SAME set through to `applyRedaction`/`config.redact` correctly; the bug was isolated to this one function's one line. Confirmed via `grep` that no other package has a similar tracking-resolver mechanism (this pattern is `@aart/engine`-only).

**Test fallout, all fixed in the same pass (the bug being fixed is exactly why these needed updating — they encoded the wrong behavior as "expected"):** `packages/engine/src/redaction.test.ts` (`createTrackingSecretResolver` describe block — now asserts VALUES are tracked, plus a new test for the `undefined`-value guard), `packages/engine/src/step-executor.test.ts` (three tests: the two pre-existing "redaction routing" tests, plus this same session's own newly-added `recordLlmCall`-redaction test from reconciliation ledger item 6 — which inherited the SAME buggy assumption when written, since it was modeled on the pre-existing tests before this bug was known).

**Residual risk / what this does NOT cover:** this fix makes redaction correct going forward; it does not retroactively re-redact anything already persisted by a pre-fix run (not applicable here — no production data exists yet, this is pre-publish). Confirmed no other package independently reimplements this tracking pattern. Recommend the Phase 3 security pass explicitly re-verify this exact mechanism adversarially (not just via this regression test) given its severity.

Tests: `packages/mcp/src/real-context.test.ts` (the test that found it, now passing), `packages/engine/src/redaction.test.ts`, `packages/engine/src/step-executor.test.ts`. Full suite run 3 times consecutively post-fix to rule out non-determinism (a security-critical fix warrants more than one green run): 204 files / 2005 tests, stable all 3 runs.

### A36 — S9 Phase 3 adversarial security findings F1/F2/F4/F5 resolved (redaction chokepoint); F5's fix generalizes the codebase's own existing "can't redact pixels" posture rather than inventing a new one

All four findings from `packages/governance/src/redact-adversarial.test.ts` (F1, F2, F4) and `packages/mcp/src/redaction-adversarial.test.ts` (F5) are fixed. Every adversarial test that documented a finding is relabeled and now asserts the fixed behavior — see each test's own comment for the exact before/after. Full list of flipped/added test names at the end of this entry.

**F1 — a resolved secret value used as an OBJECT KEY was never scanned.** `applyReplacements` (`packages/governance/src/redact.ts`) recursed into object VALUES only (`out[key] = applyReplacements(v, ...)`, copying `key` verbatim) — a realistic trigger is a group-by/index-by aggregation keyed on a field whose value is a resolved secret (`{ [secretToken]: [...] }`). Fix: the object branch now runs the key through the same `applyStringReplacements` core every string field already used, via a small refactor that extracts that core into its own function (also reused by F2's number/boolean branch below). Still not a field-NAME allowlist (this codebase's own hard rule, ADR-10's rejected-alternative rationale, both unchanged) — nothing inspects what a key IS, only whether its literal text contains a resolved secret VALUE, the identical test every value already got. On the vanishingly rare chance two distinct original keys redact to the identical string, the later write simply wins, same as any plain-JS duplicate-key collision — a data-fidelity nicety, not a security property (the secret not leaking is unaffected either way).

**F2 — redaction was string-only, in TWO compounding ways, both fixed:**
1. **Governance layer** (`redact.ts`'s `applyReplacements`): a resolved secret coinciding with a NUMBER or BOOLEAN record field (e.g. a block that parses a numeric OTP/PIN and returns `{ code: 782341 }` as a real `number`, not a string) was never scanned — the function had no branch for these types at all, only `string`/`Array`/`object`. Fix: a new branch stringifies the value, scans it through the same core, and — only if something actually matched — returns the redacted STRING; an unmatched number/boolean passes through completely unchanged (same type, same value), so this doesn't gratuitously turn every numeric field in every record into a string. When a secret genuinely is a number this DOES change that field's type from number to string in the persisted record — documented as a deliberate side effect (there is no numeric way to spell `[REDACTED:...]`, and leaking the secret is not the alternative).
2. **Engine layer, the compounding cause** (`packages/engine/src/redaction.ts`'s `createTrackingSecretResolver`): `SecretResolver` is typed `(name: string) => unknown`, but only `typeof value === "string"` resolved values were ever added to the tracked-refs set — a resolver that legitimately returns a raw number/boolean/bigint never entered the scan set AT ALL, so even fixing (1) alone would have nothing to search for. Fix: a new `toCanonicalSecretString` helper stringifies number/boolean/bigint canonical forms into the set at the moment of resolution. Deliberately excludes `null`/`undefined` (tracking the literal string `"null"`/`"undefined"` would redact every ordinary null-shaped field in every run — a catastrophic over-redaction bug, not a fix) and excludes objects/arrays (a composite isn't itself a flat scalar to string-match against).

**F4 — overlapping secrets were applied in Set-insertion order, no longest-match-first sort.** If a SHORTER secret that is a substring of a LONGER one was resolved first, its pattern got tried first, consuming the shared substring and leaving the longer secret's non-overlapping fragment (e.g. a `"prefix-"` portion) exposed in the persisted record. Fix: `Replacement` now carries a `literalLength` (the actual matchable substring length — deliberately NOT `pattern.source.length`, which `escapeForRegex` can inflate, e.g. `"."` -> `"\."` doubles it, the wrong quantity to sort by), and both `redactRecord` and `redactRecordWithNames` sort the full replacements array by `literalLength` descending before `applyReplacements` ever runs — longest match always gets first crack at the text, independent of insertion order. Marker NUMBERS are unaffected (still assigned by Set-insertion order, preserving "same secret value -> same marker within one call"); only which pattern is TRIED first changed. Because F1's key-scan and F2's number/boolean-scan both route through the same shared `applyStringReplacements` core against the same sorted array, this ordering fix covers all three automatically, not just the original plain-string case.

**F5 (priority) — artifact bytes bypassed the redaction chokepoint entirely.** `ctx.writeArtifact` (`packages/engine/src/step-executor.ts`'s `buildBlockContext`) called `config.store.artifacts.put()` directly with the block's raw bytes — the one persist path in this package that never routed through `applyRedaction`; RunRecord/StepTrace/wait-checkpoint persistence all did. Fix generalizes this codebase's own existing, pre-fix posture (`packages/blocks-core/src/browser/screenshot.ts`'s `maskSelectors` comment: "text-based redaction doesn't work on a bitmap") from one block to every artifact write, split on declared MIME type:

### A40 — Load/soak sanity E2E (plan §4) found a genuine production bug: a worker under real sustained load gets stuck in an infinite re-claim loop on its own already-finished runs, starving every other pending run forever

**This is the most severe bug found this session.** Not a redaction gap, not a broken one-shot tool call — a worker process that, under real multi-run load, permanently stops making progress on new work after its first `maxConcurrentRuns` runs complete, silently, with no error, no crash, no log line an operator would necessarily notice as alarming (the claim/complete cycle looks superficially like healthy activity in the logs — it just never touches anything new). No test in this codebase's history had ever pushed more than a small, sequential handful of runs through a real `startWorker` claim loop before this session — precisely why the plan flagged this as unattempted.

**Reproduction (concrete — a debug script against the real composition, not inferred from reading code):** 20 runs triggered against a real `startWorker` (`maxConcurrentRuns: 3`). The first 3 runs claim and complete correctly. Every run after that: stuck. Logging every worker log line (the default `logSink` is `noopSink` — silent by default, which is itself part of why this was easy to miss) showed the SAME TWO run ids being claimed, "finished," and released **in a sub-millisecond tight loop, forever** — never once reaching any of the 17 still-pending runs.

**Root cause, traced precisely:** `worker.ts`'s `executeOneClaim` success path called `store.jobQueue.release(runId)` unconditionally after every successful `executeClaimedRun` — including when the run being "executed" was ALREADY terminal. `run-lifecycle.ts`'s real `executeRun` correctly treats an already-`completed`/`failed`/`cancelled`/`waiting` run as an idempotent no-op (returns it unchanged, does not re-run steps) — so nothing ever threw, nothing ever looked broken from inside a single claim. But `JobQueueStore.release` clears `claimedBy` to `null` and **leaves the row in place** — and `listClaimable`'s own documented contract ("never claimed, or claimed with an expired lease") cannot distinguish a released-because-finished row from one that was genuinely never claimed. The instant a run finished and its entry was released, it became claimable again, immediately, forever — a self-sustaining loop that starves every other row in `job_queue` for as long as the worker runs, since `claimTick`'s own admission-control loop (`while (claiming && claimedRunIds.size < maxConcurrentRuns)`) keeps finding "claimable" work in the SAME 2-3 already-done rows before ever reaching the genuinely-pending ones behind them in `listClaimable`'s result order.

**The comment on the code being replaced was itself the tell — a documented but never-verified assumption:** "A run correctly checkpointed into `waiting` by the engine has already had its claim released as part of that checkpoint (S1's job)." Verified directly, this session: `wait-machine.ts` and `run-lifecycle.ts` (`@aart/engine`) call exactly one `job_queue` method, ever — `enqueue`, at trigger time. Neither ever calls `release` or `remove`. `job_queue` lifecycle for a claimed run has ALWAYS been entirely `@aart/server`'s own responsibility — the "backstop" framing in the old comment was wrong about there being a primary mechanism it was backing up.

**Fix:** `.release(runId)` -> `.remove(runId)` in `worker.ts`'s `executeOneClaim`. Verified this is correct for every status a successfully-returned `executeClaimedRun` can leave a run in (`executeRun`'s own loop never returns while still `"running"` — only completed/failed/cancelled/waiting): completed/failed/cancelled obviously never need to be reclaimed again; `waiting` doesn't either, because resumption (`resumeManual`/`resumeBySignal`/`resumeApproval`/`resumeTimerWait`) drives execution forward itself (`engine.ts`'s `continueAfterResume` calls `runStepsLoop` directly) — nothing about resuming a wait depends on a worker re-claiming it from `job_queue`. Confirmed no existing test depended on the old `release`-and-leave-present behavior: full `worker.test.ts` (15 tests, all reclaim-sweep-related, all exercise `reclaim.ts`'s own separate `release`/`remove` calls, untouched by this fix) re-verified green.

**One of my own E2E tests (A37, worker-kill) had baked in an assertion matching the OLD, buggy behavior** (`expect(finalJobQueueEntry).toMatchObject({ claimedBy: null, reclaimCount: 1 })` — asserting the row still existed after completion) — updated to assert the row is now genuinely gone (`store.jobQueue.get(runId)` resolves `undefined`), matching the corrected, actually-correct behavior. Re-verified: 4/4 clean runs (worker-kill + load-soak together).

**The load/soak test itself** (`packages/server/src/e2e/load-soak.e2e.test.ts`, in-process — deliberately not a spawned child process, unlike the SIGKILL-driven E2E tests, since directly sampling `process.memoryUsage()` for the actual worker doing the work is more meaningful than querying a child process over IPC for a memory-sanity concern): 20 runs, `maxConcurrentRuns: 3`, a real ~80ms-delay block (long enough that concurrency is genuinely observable, not just theoretically possible). Checked for an "attended vs unattended" mechanism as an alternative reading (the brief flagged this as one possible needle-threading) and ruled it out: no such field or concept exists anywhere in `@aart/types`, spec, or architecture (no `RunRecord.attended`, nothing comparable). The mechanism the spec/architecture actually built for authoring-loop freedom is `dev`-vs-`governed+` (a MODE a caller opts into), not a property of which surface issued the call — confirmed by `getGrantedCapabilities`'s own pre-existing, correct `trustMode === "dev"` branch, which is precisely this escape hatch already implemented and already tested (`packages/governance/src/capability.test.ts`) in isolation. The bug is entirely in how a real run's `trustMode` input reaches that already-correct function.

**Where it actually broke — a genuine split-brain between two independently-resolved trust-mode signals, not a single bug in one place.** `getGrantedCapabilities`'s policy function is correct. The bug is in the ADAPTER that resolves its `trustMode` argument for a real run (`packages/mcp/src/real-context.ts`'s `createGetGrantedCapabilities`, before this session):

```ts
let trustMode: TrustMode = "dev";                    // unconditional, un-overridable
if (environment) { /* resolve from Environment.config.trustMode, correctly */ }
```

`environment` here is `TriggerRunInput.environment` (architecture §4.6: "Threaded through to `getGrantedCapabilities` on every step dispatch for this run's lifetime") — and **nothing in the shipped code ever supplied one, anywhere**, for two independent reasons:

1. `RunWorkflowInput` (`packages/mcp/src/handlers/execution.ts`'s `runWorkflowHandler`, shared verbatim by CLI `aart run` — `packages/cli/src/commands/authoring.ts`'s `runCommand` — and MCP `aart_run_workflow`, per this repo's own three-clients principle) has no `environment` field at all; it never existed as a concept on this surface. Every direct run, forever, resolved `trustMode = "dev"` inside the capability chokepoint — full, unconditional grant — **regardless of `ctx.trustMode`**, the SEPARATE, CORRECTLY-resolved ambient trust mode (`context.ts`'s `resolveTrustModeFromEnv()`, defaulting to `"governed"` per spec §17.2, `AART_TRUST_MODE`-overridable) that `runWorkflowHandler` was already passing as `approvalMode: ctx.trustMode` into `triggerRun` the whole time — correctly recorded onto `RunRecord.approvalMode` for audit purposes, but never once consulted by the actual dispatch-time enforcement. `aart_validate`'s finding wording is produced from this SAME correct `ctx.trustMode`, via `createRealGovernancePort(catalog.blocks, trustMode)` feeding `ValidationContext.trustMode` — which is exactly why the finding read as if it should have blocked: validate and dispatch were silently reading two different trust-mode sources that happened to agree everywhere except the one place that mattered.
2. Independently, on the trigger-fired (webhook/github/slack/poll/queue/database/email/file/sdk — every type sourced from `Deployment.triggerConfig`) side: `Deployment.environmentId` (a real, populated field on every deployment, already used to FILTER which deployments load — `loadTriggerBindingsFromDeployments(store, {environmentId})`, A45) was never carried ONTO the resulting `TriggerBinding` (`packages/server/src/triggers/registry.ts`'s `deploymentToBinding` set `deploymentId` but not `environmentId`), and `StartRunParams` (`packages/server/src/engine/boundary.ts`) had no `environment` field for `processTriggerIntake` (`packages/server/src/triggers/intake.ts`) to pass one through even had it been available. An unattended, deployed, webhook-fired execution of an unapproved workflow against a `production`-trust-mode environment got the exact same accidental unconditional-grant bypass as a direct `aart run` — arguably the more serious half of this finding, since unattended/triggered execution is precisely the case the trust-mode design exists to protect (nobody is watching a webhook fire).
3. Worker-claimed execution (`EngineBoundary.executeClaimedRun` → `Engine.executeRun`) needed no separate fix once (1)/(2) closed: `environment` is captured ONCE into `RunRecord.params.environment` at trigger time (`packages/engine/src/run-lifecycle.ts`'s `environmentOf(run)`) and re-read on every step dispatch for that run's ENTIRE lifetime, including worker-resumed continuations after a wait or a worker restart — this is the same chokepoint, not a fourth independently-behaving copy. Verified directly, not assumed: a dedicated test (`boundary.test.ts`) constructs a real capability-policy engine and proves `executeClaimedRun` denies/allows identically to the direct-run path, rather than inferring it from the plumbing alone.
